## 一、研发背景

### 1.1 要解决的问题

日常上网的账号密码散落在三个地方：浏览器自带密码管理器、手机备忘录、脑子里。带来的实际困扰是：

| 困扰 | 具体表现 |
|---|---|
| 记不住 | 每个站点密码规则不同，改密码后记混 |
| 找不回 | 浏览器密码管理器跨浏览器不通用，换设备就丢 |
| 不敢存 | 存到云端不放心；存到本地记事本又等于明文裸奔 |
| 填得烦 | 每次登录都要「打开管理器 → 搜索 → 复制账号 → 复制密码 → 粘贴」五六步 |

### 1.2 一个必须先说清的技术事实

**桌面应用无法读取浏览器里的网页内容。** 这是浏览器的安全沙箱，不是能力缺陷。所有「自动识别登录框、右键一键填充」的功能，都必须由浏览器扩展完成。

可选方案只有三条，只有一条成立：

| 方案 | 可行性 | 结论 |
|---|---|---|
| 用 macOS 辅助功能 API 读网页元素 | 需要用户授予「辅助功能」权限，WebView 内部元素暴露不稳定，表单结构千变万化 | ❌ 不可靠，且用户会害怕 |
| 让用户在本应用内置浏览器里登录 | 只能覆盖「在密钥库里登录」，不是日常路径 | ❌ 场景错位 |
| **浏览器扩展 + Native Messaging** | Chrome MV3 / Safari Web Extension 原生支持，右键菜单是扩展标准能力 | ✅ 唯一正解 |

因此产品形态从一开始就确定为**一个产品、两个进程**：

```
┌──────────────────────────┐         ┌─────────────────────────────┐
│  密钥库.app（Tauri）      │         │  密钥库扩展（Chrome MV3）    │
│  ├ 主窗口 / 菜单栏图标    │◄───────►│  ├ 识别登录框                │
│  ├ Rust 加密内核          │ Native  │  ├ 右键菜单 / 内联钥匙按钮   │
│  ├ SQLite（密文）         │ Messa-  │  ├ 自动保存与页面内提示      │
│  └ 触控 ID / 钥匙串       │ ging    │  └ 执行填充                  │
└──────────────────────────┘         └─────────────────────────────┘
              ▲                                      │
              └───────────── 用户 ↘ 浏览器 ───────────┘
```

### 1.3 设计出发点

三个明确的取舍贯穿全部决策：

1. **本地优先，不做云端**。数据只存在这台 Mac 上，磁盘上是 AES-256-GCM 密文，项目代码里没有任何网络请求。
2. **不打断用户**。保存不弹需要决策的对话框，填充不用切换窗口，锁定不强制频繁输密码。
3. **安全边界要能被理解**。加密参数、数据位置、锁定规则都在界面里可见，而不是藏在宣传语里。

## 四、技术架构

### 4.1 技术选型

| 层 | 选择 | 理由 |
|---|---|---|
| 桌面外壳 | **Tauri 2**（Rust + 系统 WebView） | 体积约 8 MB，Electron 约 150 MB；且加密逻辑天然留在 Rust 进程 |
| 前端 | React 19 + TypeScript + Vite | 组件化、类型安全、构建快 |
| 内核 | 独立 Rust crate（`keylite-core`） | 不依赖 UI，可独立单测 |
| 存储 | SQLite（WAL 模式） | 单文件、事务可靠、支持并发读 |
| 扩展 | Chrome MV3 | 右键菜单、Native Messaging 均为标准能力 |
| 生物识别 | `LAContext`（objc2 绑定） | 系统级指纹验证 |

### 4.2 进程与通信

```
浏览器页面
   │  content script（隔离世界，读 DOM、执行填充）
   ▼
扩展后台（service worker）
   │  chrome.runtime.sendNativeMessage
   ▼
keylite-host（Chrome 拉起的子进程，只做字节搬运）
   │  Unix socket（~0600，仅当前用户可读写）
   ▼
密钥库.app（Rust 进程：解密、校验、落盘）
```

**为什么需要 `keylite-host` 这一层**：Chrome 的 Native Messaging 只认 stdio 管道，且每次按需拉起新进程，无法与已运行的应用共享内存。所以由它把 stdio 帧桥接到应用的 Unix socket 上。

**通信协议**（4 字节小端长度前缀 + UTF-8 JSON）

| 请求 | 用途 |
|---|---|
| `fill.query {origin}` | 取本站点条目摘要（**不含密码**） |
| `fill.exec {id, origin}` | 取明文凭据（要求已解锁 + 注册域一致） |
| `save.candidate {url, origin, username, password}` | 提交登录后自动保存 |
| `item.update_password` / `item.delete` | 冲突更新 / 撤销 |
| `generate {length}` | 生成强密码 |
| `app.show` | 把主窗口叫到前台 |

### 4.3 密钥层级

```
主密码 ──Argon2id(salt)──► KEK ──AES-GCM 解包──► DEK（32 字节数据密钥）
                                                    │
                              每条记录 ──AES-256-GCM(DEK, 随机 nonce)──► 密文字段
```

- **改主密码只需用新 KEK 重新封装同一个 DEK**，不需要重写全库数据（毫秒级）
- 触控 ID 通路：DEK 的另一份副本存进登录钥匙串，读取前必须通过系统指纹验证
- 锁定 = 内存中的 DEK 立即清零（`Zeroizing`）

## 五、用户体验说明

### 5.1 四条主路径（实际步骤数）

| 场景 | 传统做法 | 密钥库 |
|---|---|---|
| **存密码**（首次登录某站） | 打开管理器 → 新建 → 复制域名/账号/密码 → 粘贴（5 步，跨窗口） | **0 步**：提交后自动保存，页面角落提示一句 |
| **取密码**（再次登录） | 打开管理器 → 搜索 → 复制账号 → 复制密码 → 粘贴（5 步，跨窗口） | **2 步**：点进输入框 → 点小钥匙 → 选账号（全程不离开页面） |
| **找条目**（不记得账号） | 记得关键词才能搜到 | 内联下拉直接列出本站全部账号，不需要记得 |
| **解锁** | 每次都输主密码 | 按一下指纹 |

### 5.2 关键体验决策与理由

**① 默认自动保存，而不是弹窗询问**

让用户切到桌面端点「保存」，等于把成本从 0 次点击抬到 3 次（切窗口、找按钮、切回来）。所以默认直接保存，用**页面内提示 + 6 秒撤销**替代确认。想逐条确认的用户可在设置里切到「先询问」。

**② 只有一种情况会打断你：密码冲突**

同站点同账号已存在但密码不同时，页面弹「更新密码？/ 保持原样」。原因很实在：手滑输错一个字符导致登录失败，如果静默保存就会**用错误密码覆盖掉原本正确的密码**，用户彻底登不进去。这是密码管理器唯一不能自动化的判断。

**③ 内联钥匙按钮是主路径，右键是兜底**

右键菜单要求用户先记得「这个应用支持右键」。内联按钮出现在用户本来就要点击的地方（输入框），零学习成本。右键保留给熟悉键盘和高级用户。

**④ 不打断的三条硬规则**

- 保存提示不抢焦点（页面内提示条，不是系统弹窗）
- 填充后不跳转、不刷新、不改动页面其他内容
- 失败时一定给可见反馈（锁定了、站点不匹配、没抓到密码，各有明确文案）

**⑤ 锁定策略从「安全优先」改成「不打扰优先」**

初版默认 15 分钟自动锁定，但计时器只统计应用窗口内的活动——用户在 Chrome 里忙 15 分钟回来就被锁，反复输主密码。现在的策略：

- 默认**不**空闲锁定（只在手动 ⌘L、退出应用时锁）
- 即使开启空闲锁定，**在浏览器里使用密钥库也算活动**
- 有了触控 ID 后，锁定成本≈0，建议重新开启 5 分钟

**⑥ 关窗口不等于退出**

窗口关掉后应用缩进菜单栏继续运行，浏览器扩展照常工作。用户不需要「为了用扩展而一直开着窗口」。同时设了一条安全阀：**菜单栏图标关掉时，关窗口会直接退出**，避免出现「窗口没了、图标也没了、进程还在跑」的死局。

### 5.3 失败路径的体验设计

| 情况 | 用户看到什么 |
|---|---|
| 密码库锁定 | 「密钥库已锁定，这次登录没有保存」+ **去解锁**按钮（一键把窗口叫到前台） |
| 站点不匹配（防钓鱼拦截） | 「这条属于 github.com，当前页面是 qq.com。同一个账号在不同网站要分别保存。」 |
| 没抓到密码 | 「没抓到密码，这次登录没有保存」 |
| 该站点没有条目 | 内联按钮不出现（不打扰），右键提示「这个网站还没有保存的条目（域名）」 |
| 扩展被重载 | 旧脚本静默退场，不刷错误；刷新页面即恢复 |

### 5.4 性能与资源

- 正式打包后体积预计 8–10 MB 量级（Electron 同类应用通常 150 MB 以上）；开发版因含调试符号会大很多
- 解锁耗时：Argon2id 约 120–200 ms（M 系列芯片）；触控 ID 走系统验证
- 列表与搜索在内存中完成，2000 条以内无感知延迟
- 扩展不向页面主世界注入任何脚本，自己的 UI（钥匙按钮 / 提示条 / 选择器）全部渲染在 Shadow DOM 内，页面样式影响不到它，它也不改页面样式

## 六、信息安全说明

### 6.1 威胁模型

| 威胁 | 是否防御 | 措施 |
|---|---|---|
| 数据库文件被拷走（U 盘 / 云盘同步 / 备份泄露） | ✅ | 密码等敏感字段 AES-256-GCM 密文，主密码不落盘 |
| 主密码被暴力破解 | ✅ | Argon2id（m=64 MiB, t=3, p=4），单次约 150 ms，离线爆破成本高 |
| 钓鱼站骗取密码 | ✅ | 注册域（eTLD+1）严格匹配，`github.com.evil.cn` 无法命中 `github.com` 的条目 |
| 恶意网站通过扩展偷密码 | ✅ | 扩展取明文要求「已解锁 + 站点一致」，且必须经白名单扩展 ID 调起 |
| 其他扩展冒充密钥库 | ✅ | Native Messaging 清单 `allowed_origins` 只放行本扩展 ID |
| 本机其他用户读取 | ⚠️ 部分 | socket 权限 0600、数据库在用户目录下；同一用户下的进程仍可能读到文件（内容仍是密文） |
| 设备丢失 | ⚠️ 部分 | 内容加密，但**元数据（站点名、账号）是明文**，见 6.4 |
| 内存被 dump | ⚠️ 部分 | 明文用完即 `zeroize`；但已解锁期间 DEK 必须在内存中 |
| 剪贴板残留 | ✅ | 复制后按设置延迟清空，且只清自己写入的那次 |
| 云端泄露 | ✅ | 没有任何云端，代码中无网络请求 |

### 6.2 加密实现细节

| 项 | 值 |
|---|---|
| 内容加密 | AES-256-GCM，每条记录独立随机 12 字节 nonce |
| 附加认证数据（AAD） | 条目 id —— 防止密文在条目之间被搬运 |
| 密钥派生 | Argon2id，m=64 MiB，t=3，p=4，16 字节随机 salt |
| 数据密钥 | 32 字节随机 DEK，用 KEK 封装后存库（60 字节 = 12 nonce + 32 密文 + 16 tag） |
| 主密码 | **不存储**，只存 salt 与封装后的 DEK |
| 触控 ID 副本 | 登录钥匙串（service `dev.keylite.app`），读取前必须通过 `LAContext` 指纹验证 |
| 单测覆盖 | 密文篡改检测、AAD 跨条目防搬运、落盘无明文断言、错误密钥拒绝、nonce 唯一性 |

### 6.3 扩展侧的安全约束

- **权限最小化**：只申请 `contextMenus / nativeMessaging / storage / scripting / activeTab`，不申请全站网络权限
- **不存密码**：扩展不缓存任何凭据，`fill.query` 返回的列表**不含密码字段**（有单测断言响应里连 "password" 这个词都不出现）
- **不联网**：扩展代码没有任何网络请求
- **取明文三道关**：① 桌面端必须已解锁 ② 条目注册域与当前站点一致 ③ 调用方必须是白名单扩展 ID

### 6.4 明确的残余风险（如实披露）

1. **元数据是明文**。名称、网址、域名、用户名以明文存储，目的是让列表和搜索秒开。拿到 `vault.db` 的人能看出你注册过哪些网站、用什么账号，但**看不到任何密码**。如需连元数据一起加密，需改成整库加密（代价是搜索性能）。
2. **未签名构建下的钥匙串 ACL**。macOS 的「钥匙串项 + 生物识别 ACL」需要开发者证书签名才能生效，`tauri dev` 的未签名二进制拿不到。当前实现是「先过系统指纹验证，再读钥匙串副本」——同一用户下的其他进程若直接读取该钥匙串项（macOS 通常会弹授权框），可绕过指纹。**正式签名打包后可升级为生物识别 ACL 版本，接口不变。**
3. **扩展是相对薄弱的一环**。content script 运行在页面上下文中，理论上可能被极端手段干扰；但凭据只在用户明确操作（点选账号）时才从本机取出，且取出后立即填入。
4. **已解锁期间的风险**。应用解锁后 DEK 在内存中，此时同一用户下的恶意程序可能读取进程内存。这是所有本地密码管理器的共同边界。
5. **没有「忘记主密码」的找回**。这是设计而非缺陷：任何找回机制都会成为后门。

## 七、适用场景与边界

### 7.1 适合

- 个人 Mac 上管理几十到几百个网站账号
- 希望数据完全不出本机、不接受云同步
- 主要在 Chrome / Edge / Brave 里登录各种系统（含企业 OA、后台管理、SaaS）
- 需要两步验证码集中管理（内置 TOTP，不用另开验证器 App）

### 7.2 不适合

- **多人共用一台 Mac**：v1 是单密码库、单主密码，没有多账户隔离
- **需要多设备同步**：同步功能在 M5，当前只有加密备份导出
- **需要团队共享密码**：不在规划内
- **Safari 重度用户**：Safari 扩展在 M3
- **需要浏览器之外的自动填充**（桌面 App、SSH、Wi-Fi 密码）：不在当前范围

值得说明的几项**防回归断言**：

- 密文篡改必须解密失败；AAD 不一致必须失败（防止密文在条目间搬运）
- 写入数据库后，原始密码字符串**不得出现在任何数据库文件中**（含 WAL）
- `fill.query` 的响应里不得出现任何密码字段
- 钓鱼域 `github.com.evil.cn` 查询必须返回 0 条
- 登录成功后页面清空输入框，仍能正确保存（快照兜底）

### 8.3 研发过程中的典型问题（用于说明工程质量）

| 问题 | 教训 |
|---|---|
| 浏览器扩展被重载后，旧页面残留脚本报 `Extension context invalidated` | 所有消息发送统一走安全封装，检测到失效即静默退场 |
| 右键菜单刷新存在竞态，报 `duplicate id` | 所有菜单操作串行化 |
| Tauri 的 WKWebView 不实现 `window.confirm`，删除按钮点了没反应 | 改用应用内确认弹窗 |
| `input[type=submit]` 没有 `textContent`，点击检测取到空串 | 标签取 `textContent \|\| value` |
| 登录跳转导致 IPC 消息丢失 | `sessionStorage` 暂存 + 新页面补发 |

## 九、数据位置与迁移

### 9.1 存储位置

```
~/Library/Application Support/dev.keylite.app/
├── vault.db          SQLite 主库（条目、密文、KDF 参数、设置）
├── vault.db-wal      WAL 预写日志（运行中会有，退出后合并）
├── vault.db-shm      WAL 共享索引
├── ipc.sock          浏览器扩展通信通道（权限 0600）
└── bin/keylite-host  扩展调起的桥程序
```

触控 ID 的密钥副本：系统钥匙串，service = `dev.keylite.app`。

### 9.2 备份

拷贝 `vault.db` 即可（建议先退出应用让 WAL 合并）。换一台 Mac，只要记得主密码，拷回去就能解。也支持从应用内导出加密备份。

### 9.3 彻底卸载

```bash
rm -rf ~/Library/Application\ Support/dev.keylite.app
security delete-generic-password -s dev.keylite.app
```

删掉即彻底消失——没有后门、没有找回、没有云端副本。
